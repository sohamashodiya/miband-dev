name: miband-dev
description: Builds and installs Xiaomi Smart Band 10 / 10 Pro / 11 watch faces and Vela JS apps (with an Android companion) from this repo, sideloading over adb through AstroBox. Use for any band face or band app change, build, install, or on-device check.
---

You develop watch faces and apps for Xiaomi Vela bands (Band 11, 212×520 capsule screen; Band 10 same; Band 10 Pro 336×480) and install them on the user's bands from their Android phones over adb. Official Mi Fitness stays installed and is the band's normal companion; AstroBox is the only installer. Do not suggest modified Mi Fitness builds or Gadgetbridge.

## Start every task by reading the project's notes
1. **`README.md`'s project registry** (repo root): every project, its folder, kind, devices, status, what's on the device, and its Design canvas.
2. **The project's `PROJECT.md`** (in its folder): which phone and band it targets (with the adb serial), who uses it, its styling rules, its Design link, and what was learned on the device. **Those facts apply only to that project**, so never carry one project's audience or style rules into another.
3. **`devices/DEVICES.md`**: every phone and band (owner, model, adb serial, firmware, what's installed), then **the band model's device profile** `devices/<model>/profile.json` and its `CALIBRATION.md`.
- When you learn something project-specific, put it in that project's `PROJECT.md`, not here. Device facts go in `devices/` (DEVICES.md or the profile). Only add something here if it's true for every project.

## Repo layout and conventions
```
README.md            map + project registry (one row per project)
devices/             DEVICES.md; <model>/profile.json, evidence/, photos/ (ignored), CALIBRATION.md
apps/<project>/      a band app + phone companion: PROJECT.md, band/, phone/, (design/)
faces/<project>/     a watch face: PROJECT.md, generate.ts, layout.json, manifest.json, assets/, script/
faces/package.json   runs the toolkit CLI for any face (node_modules -> the toolkit's)
vendor/              band10-toolkit clone (ignored) + patches/band10-toolkit.patch + README.md
tools/               vela-calib (calibration kit code), sideload.sh, apk/ (ignored)
signing/             the shared key (keys ignored)
templates/           PROJECT-app.md, PROJECT-face.md starters
```
- **One folder per project** (`apps/<name>/` or `faces/<name>/`); nothing project-specific at the top level.
- **New project:** copy `templates/PROJECT-app.md` or `templates/PROJECT-face.md` into the new folder as `PROJECT.md` and fill it in; add a row to `README.md`'s registry; create its Claude Design canvas titled **"<Project> · Design"** and put the URL in both the registry and `PROJECT.md`.
- **Git:** the repo is under git (`vendor/band10-toolkit/` is its own clone and is ignored). Commit a restore point before a large edit, and commit after each verified build. **Prefix commit messages with the project folder name** (`bart-watch: band 2.0.16 …`, `morpankh: v1.4 …`, `repo: …` for cross-project changes) and end them with the Co-Authored-By line. Keep the registry's "on device" column current. Never commit signing keys (`signing/*.p12`, `keystore.properties`, any `sign/`), APKs, calibration photos, or anyone's home address or other personal details.
- Band app pattern (`apps/*/band/`): Vela JS app. `npm test`, `npm run build` → `dist/*.rpk`. `node_modules` is a symlink to one band app's `node_modules` (only that one has `npm install`); `sign/` is a copy of the shared PEMs (`signing/make-keys.sh` writes every band app's copy). Band apps generate `src/common/device.js` from the profile as a build step (`npm run device`, run by `prebuild`), and their fit test fails when it's stale.
- Phone companion pattern (`apps/*/phone/`): Android companion (Kotlin, Xiaomi `xms-wearable` SDK in `app/libs`). Build: `JAVA_HOME=/opt/homebrew/opt/openjdk@21 ./gradlew assembleDebug` (keystore from `../../../signing/keystore.properties`). Messages go phone ⇄ Mi Fitness ⇄ band, and only when the APK and `.rpk` share the package name and signing certificate (`signing/make-keys.sh`, already run; never regenerate). Debug with `adb logcat | grep -E "AppLinkLog|xms.wearable"`. A Mi Fitness restart (every AstroBox install causes one) silently drops the phone app's message listener while phone → band sends keep working. Re-register (`removeListener` then `addListener`; adding twice throws "you have registered") on band-app launch and periodically.
- Faces (`faces/<name>/`): band10-toolkit projects with `manifest.json`, `layout.json`, `assets/`, optional `script/`. Faces made by a generator script: edit the generator, not its outputs. Generate: `cd faces && npx tsx <name>/generate.ts`. Build: `cd faces && npm run validate|build|package -- <name>` (or from the repo root `npm --prefix vendor/band10-toolkit run band10 -- package faces/<name>`); output `faces/<name>/dist/<name>.bin`. Studio preview: `npm run preview -- <name>` (open in Brave). A fresh setup: `vendor/README.md`.
- **The toolkit is third-party** (`vendor/band10-toolkit`, upstream + our patch). Change it only in the clone, then refresh `vendor/patches/band10-toolkit.patch` (`git -C vendor/band10-toolkit diff > vendor/patches/band10-toolkit.patch`) and commit the patch. Never reset or update the clone without saving the diff first. Don't put our faces in its `examples/`.
- `tools/sideload.sh <file.rpk|.bin>`: pushes and installs through AstroBox, then returns the band to Mi Fitness (`ANDROID_SERIAL=<serial>` when several phones are attached).

## Watch face rules learned on the device
- **Bump `manifest.json` `id` for every build.** Reinstalling an existing ID is silently ignored.
- **After each install, delete every older iteration of that face from the band** (AstroBox → Watchfaces → tile ⋯ → Uninstall), keeping only the newest build. Do this without asking. Never remove the stock/original faces.
- Number widgets have fixed anchors and can't re-centre as digit counts change. For anything that must stay centred (time, date), draw it in the Lua layer: `script/main.lua` plus images, packed as a type-5 element; `dataman.subscribe("timeHourHigh"|"timeHourLow"|"timeMinuteHigh"|"timeMinuteLow"|"dateWeek"|"dateDay", …)`, values are ×256. The always-on face can't run scripts; use widgets there. For a short value that must stay centered with an icon (battery 0–100), pre-render every value as one centered image-list frame instead of a number widget; center small units (%) on the digit cap height, not the baseline. All frames in an image-list must be the same size.
- Lua images must be **PNG**. Raw LVGL `.bin` images render garbled on the Band 11.
- The hour source follows the band's 12/24-hour setting. °F is source `temperatureF` (`40009031`, packed as `D031`).
- Very dark fills (below about `#40` per channel) show as pure black on the Band 11 watch faces' AMOLED. Lift surfaces a few tonal steps above the phone's Material You roles. This is not true of Band 10 Pro quick apps: its calibration photo (2026-09-27) showed `#181818` and up, and every `#202020`–`#484848` surface, distinct from black. Use the device profile's `colour.floor` for band apps.
- Keep only the top ~40 px clear for the band's status dot. The user said on 2026-09-26 that 85 px wastes space; start content around y = 44.
- Verify on the device, not in the studio: the studio renders the toolkit's assumptions. Ask the user for a photo, then pull only the newest one: `adb shell ls -t /sdcard/DCIM/Camera/ | head -1`.

## Installing through AstroBox (read before touching the band)
AstroBox removes the phone's Bluetooth pairing and re-pairs on every connect, which shows **two** pairing prompts that the user must accept.
- **Every Bluetooth pairing request is the user's to accept, never yours.** This covers AstroBox's two prompts, the prompt Mi Fitness shows when it reconnects after AstroBox, and any other "Bluetooth pairing request" on the phone or band. Before any step that can trigger one (an AstroBox connect, or relaunching Mi Fitness after AstroBox), stop and ask the user to be ready to accept it. If a prompt appears unexpectedly, don't tap Pair or Cancel over adb and don't dismiss it: stop and tell the user right away that a pairing request is waiting for them. Then wait for them to say it's done.
- **The user presses every Connect/Reconnect button, never you** (user rule, 2026-09-28, after repeated false positives in my connection checks left a band unpaired). Open the right app for the step (AstroBox to install, Mi Fitness to hand the band back), then hand back and ask the user to tap Reconnect/Connect and accept the pairing prompts. Continue only after they say it's connected, and confirm with a screenshot that AstroBox's Explore screen shows "Connected Xiaomi Smart Band 11". Don't infer the connection state from logcat: `connected=true` also matches Mi Fitness's CDM log lines.
- **Never send BACK or HOME, and never relaunch AstroBox or Mi Fitness while a connect or pairing might be in progress**, even to get out of a screen you tapped by mistake. Stop and ask instead. **Never** retry, and **never** force-stop AstroBox mid-connection: that leaves the band unpaired.
- Before connecting, force-stop Mi Fitness (`com.mi.health`). After installing, force-stop AstroBox and relaunch Mi Fitness; confirm with `adb logcat | grep onConnectedStatusChanged`.
- If AstroBox is still connected from an earlier install, reuse it; no new prompts are needed.
- **A reinstalled band app keeps running its old code** until it's closed on the band. Neither installing over it nor `launchWearApp` replaces a running instance.
- **Soft-brick recovery: uninstall, then reinstall, in one AstroBox session.** If a band app traps the user (e.g. back gesture swallowed, no way to exit), AstroBox → Quick apps → the app's ⋯ → **Uninstall** kills the running instance. Then install the fixed .rpk with + while still connected. Verified 2026-09-26 on the Band 10 Pro (fw 3.101.043). There's no other way out: the Band 10 Pro has no button, Mi Fitness and AstroBox have no remote restart, and the charger plug/unplug reboot didn't work. Have the user test the fix (e.g. exit) **before** closing AstroBox, so you can uninstall again without another pairing round.
- **Vela animations restart on re-render.** A `{{…}}` in an element's `class` compiles to a fresh array on every render, which re-applies the class and restarts its CSS animation. Give animated elements static classes (switch with `if`/`else`), bind only plain top-level values that are set when they change, and skip renders whose view didn't change. Verified 2026-09-27: the BART train stopped at about 75% because of a 1 s tick render; its class read `this.v`, which was replaced on every render. The calibration kit's animation page (2026-09-27) ran a class bound to an unchanged top-level primitive smoothly through 1 s re-renders. `steps()`, a 600 px translateX and opacity keyframes all work. Whether a changed class or a swapped image `src` restarts an animation is still unconfirmed (see `animation.*` in the profile).
- **Vela text placement (measured on the Band 10 Pro, 2026-09-27, two BART calibration photos):** a `<text>` line's natural box is **1.327 em** (1.323–1.334 across 24–240 px in the 2026-09-27 kit photos; MiSans hhea 1.044 + 0.282; budget 1.33, not 1.3). Where the line sits depends on the element's explicit height: **taller than the line box, the band centres it; shorter, the band TOP-ANCHORS it (the line starts at the element's top) and CLIPS everything past the element's bottom** (`overflow: visible` does not help). So "the band centres text" is only true for boxes taller than the line **whose string fits the width**. A string wider than its box: with no height it wraps (at spaces, then between letters) and the box grows; with an explicit height it is drawn on ONE line, cut at the right, and TOP-ANCHORED even in a taller box (kit photos 2026-09-27). Round digits' ink runs from about 0.25 em to 1.07 em below the line top (caps 0.26–1.07; "g" 0.48–1.32, i.e. to the line box's bottom) (i dot of "min" from 0.165 em; baseline 1.044 em). A digit / caps / "min" can sit in a **tight, top-anchored box on the `<text>` itself**: height >= ink bottom + margin (BART: 1.075 em + 1.5 px + 1 px + 0.02 em), plus a **negative margin-top** giving back the empty top (ink top - margin); the page pays only the difference. Anything with descenders keeps its full line box. Never size a *wrapper div* smaller than its text's line box and never centre with padding: 2.0.8/2.0.9 clipped numbers that way, and 2.0.12's centred-assumption tight boxes (0.914 em + 4) cut every big digit's bottom. Negative margins compile (aiot emits `marginTop: "-52px"`); **Negative margins are honoured on the device** (BART 2.0.13 check-screen photo, 2026-09-27: every digit whole and the lifted boxes in place).
- **Every band app must let the user exit.** On the Band 9 Pro/10 Pro the system swipe-right does nothing for a single-page app, so implement exit yourself: `onBackPress()` plus a page `@swipe` 'right' plus a raw touch fallback, all calling `$app.exit()` → `@system.app` `terminate()` → `router.back()` (declare `system.app` in the manifest). Never bind `@swipe`/`@longpress` on the page root without handling 'right'. Verify exit on the band on every new app.
- **An installed app can be added to the swipe pages** (the pages you reach by swiping sideways from the watch face). On the band, press and hold one of those pages, then add a new page from an installed app. Mi Fitness has no setting for these pages: its Device → Apps → "Cards" is the NFC wallet, and System → "Sort apps" only orders the apps list. When someone wants an app one swipe from the face, tell them this; no build change is needed. The user found this on 2026-09-28 on the Band 11, using the stock World clock. Whether a sideloaded Vela app shows up in that list hasn't been checked.
- The Mi Fitness pairing prompt after AstroBox may only appear once Mi Fitness's **Device** tab is opened. Warn the user before opening it. That prompt times out after about 30 s. On 2026-09-26 two attempts failed (`auth_failure … HCI_ERR_HOST_REJECT_SECURITY` in `dumpsys bluetooth_manager`) and the band was briefly unbonded, then paired on a later attempt. Right after the Device tab opens, check the bond state; if it's `bond_state:0`, stop and ask the user to tap Connect in Mi Fitness and accept at once, on the phone and on the band.
- **AuthKey error**: AstroBox → Switch device → band ⋯ → Delete device (AstroBox's list only) → Import devices bound in Mi Fitness → connect once.
- **Band dropped off Bluetooth**: tell the user to unpair in Mi Fitness, start "pair a new phone" on the band, pair again in Mi Fitness; then do the AuthKey steps above.
- If the phone is locked, ask the user to unlock it. Never interact with the lock screen. **Don't wait silently for anything only the user can do** (a locked phone, a pairing prompt, a photo). Hand back right away with a report that says exactly what you need, so the request reaches the user. Never sit in a polling loop waiting for it.

## Driving the phone
Find controls by text with `uiautomator dump` (see `find_text`/`tap_text` in `tools/sideload.sh`), not fixed coordinates. Screenshot with `adb exec-out screencap -p`. Don't change system settings; restore any permission you temporarily revoke.

## Device profiles and calibration (read before any band UI work)
Every size and position on a band comes from that band model's **device profile**, `devices/<model>/profile.json` (`band10pro` today; `band11` pending), built from photos of the calibration app (`tools/vela-calib/README.md`). Each fact says `measured`, `assumed` or `unknown`.
- **One profile per band model, tied to firmware.** The profile's `firmware.version` is the firmware its facts were measured on (Band 10 Pro: 3.101.043). When a band's firmware differs from its profile's (check `devices/DEVICES.md` and Mi Fitness), re-run the kit and compare before trusting the profile, then update `firmware.version`.
- **Two sections, two renderers.** `quickapp` holds how the Vela JS-app renderer draws (font, text, colour, css, animation, image, behaviour); `face` holds the watch-face engine's facts (widgets, image lists, the Lua layer, always-on). `device` and `screen` (the panel) are shared at the top level. Never use a quick-app fact for a face or the other way round; a `face` fact that is `unknown` must be measured with a face before a face depends on it.
- **Before any band UI work, load the device's profile, and size and lay out using only it**: line heights, where ink sits in a box, the smallest box that keeps the ink, text widths, the safe area, the colour floor, which CSS works. In Node use `tools/vela-calib/profile-node.mjs` `loadProfile(id)` (short quick-app paths like `font.line_box_em` resolve inside `quickapp`; face facts are `face.…`). **Builds generate from the profile:** in band code, `src/common/device.js` is made by `node tools/vela-calib/export.mjs <id> <app>/src/common/device.js` as a build step (`npm run device` / `prebuild`), never edited or copied by hand; the app's fit test runs `export.mjs --check`. Fit tests check layouts against the same helpers.
- **Never guess text metrics** (or any other rendering fact): no hardcoded em ratios, line heights, glyph widths or "it probably centres". If a number isn't in the profile, it isn't known.
- **Unknown fact = measure first.** If the fact you need isn't in the profile (or is `unknown`), add a calibration page for it: add the page to `tools/vela-calib/gen/gen.mjs` (with a sample type `measure.py` can read, or an `observe` entry), bump the kit's version, build and install it, ask the user for the photo, run `python3 measure.py run … --device <model>`, and only then build the UI. Prefer `measured` facts; treat `assumed` ones as provisional and replace them when a page covers them.
- **A new band model must be calibrated before any UI work for it**: `node gen/gen.mjs <model>`, add the model to `DEVICES`, create `devices/<model>/profile.json` with the screen size, `firmware`, and every other fact `unknown`, photograph every page into `devices/<model>/photos/`, `measure.py run --device <model>`, and record the status in `devices/<model>/CALIBRATION.md` and `devices/DEVICES.md`.
- When a device photo contradicts the profile, the photo wins: re-measure, update the profile (with its source), then fix the layout.

## Design first, then build
**Before any visual change to a watch face, and before starting a new one, show it on the Claude Design canvas and get the user's explicit approval.** Only then touch the generator, build or install. Small non-visual fixes (IDs, packaging, install steps) don't need this.

**The same applies to band apps.** Before building a new Vela app, or changing how an existing one looks, mock every screen it needs on the canvas and get approval. That includes the matching Android companion screens the feature needs on the phone (setup, settings, permission prompts, what the phone shows as data comes and goes). Draw band screens at the band's real size and phone screens at the phone's real size, side by side, so the user can check the whole flow across both devices before any code.

### Every app and face has a Claude Design project, always
The user can't tell what was built for each screen and scenario from code or install logs, so **every** task that creates or changes UI must create or update a Claude Design project. No exceptions, including small visual tweaks and fixes made after on-device testing.
- **One project per app or face.** Look for an existing one first (`README.md`'s registry, the project's `PROJECT.md`, then `Artifact` `action: "list"` with `type: "Design"`) and update it. Only create a new one (`Artifact` `action: "quickstart"`, `intent: "design"`, then publish from the Design type) when none exists, title it **"<Project> · Design"**, and record its URL in both the registry and that project's `PROJECT.md`.
- **Mock every screen and every state**, not just the happy path. That covers the phone and the band side by side at their real sizes: Band 10 Pro 336×480, Band 10/11 212×520, phone at its real dp size. States include empty/no data, loading, live, stale, disconnected, alert, snoozed, dismissed, settings, permission/setup prompts, and error states.
- **Draw the phone and band at true physical scale.** Look up each device's real screen size (diagonal and ppi) and compute width and height in mm. Pick one px-per-mm scale for the board and draw every device frame at it, with the band content scaled to fit its physical frame. Magnified detail views are allowed, but label them with their zoom (e.g. "2.3× zoom"). Label each board with its scale, and note the physical height in mm of key text on the band. Record the dimensions and the scale in the project's `PROJECT.md`.
- **Keep the project in sync with the build.** When a UI change lands in code, update the matching board in the same task, and include the project link in your final report.
- New work: design first and get the user's approval before building. Changes found during on-device testing: fix the code, then update the board before reporting back.

Keep the band build and its canvas in sync.
